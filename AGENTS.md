# Рабочий процесс

Меню дополнено пунктами 9 (WEmulator отдельно) и 10 (станция в gateway + WEmulator).
Путь эмулятора и папка MPR/USO сохраняются в локальном station-menu.json.
Порт UA предлагается из выбранного protocols.json; адрес можно изменить при запуске.
Остановка WEmulator — закрытием его окна; пункт 4 управляет только процессами ПЛК.

## Интеграция WEmulator (2026-11-15)

- Контракт в claude-mem: observation #959, проект `plc-wasm`; схема подтверждена пользователем:
  шинные входы и выходы через Modbus, остальные тэги через именованный OPC UA.
- `tools/station_protocols.py` создаёт локальный `protocols.json` из папки станции, таблицы символов
  и текущей карты сборки. Адрес мастера по умолчанию `127.0.0.1:15000+N`, Unit ID N;
  секции `slaves_ip` и `slaves_port` в USO переопределяют назначения независимо.
- Новые сборки через меню передают компилятору `--station`, получают `protocols.json` рядом с пакетом.
  Запуск gateway предлагает этот файл раньше общего сохранённого пути. Старые сборки сохраняют fallback.
- OPC UA по умолчанию 4841; PKI находится вне удаляемой папки сборки, в `.local-validation/pki`.
- Несколько MPR в папке станции — ALARM и отказ загрузки/сборки. Автоматического выбора нет.
- `protocols.json` разрешён в удаляемой папке сборки, но не разрешён к публикации в Git.
- Карта содержит `signals` для отдельных переменных процесса; прежние карты без него читаются.
  Переменные процесса не превращаются в DB Snap7. Генерируемые карты и настройки остаются локальными.

## Память проекта: меню станций (обновлено 2026-11-15)

Реализация: `tools/station_menu.py`, запуск: `python tools/station_menu.py`.
При изменениях сверять эту памятку с кодом и обновлять её. Это описание поведения,
а не копия исходников станций. Проверки меню находятся в `tests/test_station_menu.py`.

### Пункты меню

| Пункт | Действие |
| --- | --- |
| 1 | Рекурсивно найти скомпилированные станции в папке из настроек, сохранить и показать список пакетов. |
| 2 | Выбрать сохранённую сборку и рекомпилировать её из исходного проекта с параметрами предыдущей сборки. |
| 3 | Выбрать сохранённую сборку и запустить станцию: Snap7-сервер или монитор без S7. В Windows открывается видимое окно. |
| 4 | Показать управляемые экземпляры станций и остановить выбранный процесс с проверкой его идентичности. |
| 5 | Изменить папку поиска и сохранить её в настройках. |
| 6 | Рекурсивно найти исходные проекты, сохранить список и показать наличие связанных сборок. |
| 7 | Выбрать исходный проект из сохранённого списка и скомпилировать его с вводом параметров. |
| 8 | Удалить несколько сборок: номера и диапазоны (`1,3-5`) либо `все`/`all`, затем просмотр путей и подтверждение `УДАЛИТЬ`. |
| 0 | Выйти из меню. |

### Настройки, поиск и сборка

- `tools/menu-settings.json` находится рядом со скриптом и публикуется по прямому
  указанию пользователя вместе с папкой `tools`, кроме Python-кэша.
  Ключи: `stations_folder`, `compiled_stations`, `source_stations`, `source_search_folder`.
  Каталоги содержат пути, названия и связи проектов со сборками; содержимого SCL в них нет.
- `.local-validation/station-menu.json` хранит локальные пути runtime/Snap7 и словарь
  `sources` для связи пакетов с исходными проектами. Этот файл также не публикуется.
- Настройки перечитываются при показе меню и перед действием. Подразделы выбора
  используют сохранённые списки без автоматического сканирования файловой системы.
  `--list` показывает сохранённый каталог; `--root` временно переопределяет папку поиска.
- `discover` проверяет пакеты `.pkg` непосредственно в заданной папке и во всех
  подпапках: заголовок SWP1, размеры и JSON-манифест. Некорректные пакеты пропускаются;
  ошибки доступа прерывают поиск. Полная проверка программы выполняется runtime.
- `discover_sources` распознаёт проекты по непустым `Program/Source` (или `Soure`)
  и `Program/Tables`. В списке исходных проектов могут быть уже собранные станции.
- `refresh_catalog` заменяет только список соответствующего поиска, в том числе
  пустым результатом. При ошибке поиска прежние настройки сохраняются.
  `update_source_links` обновляет связи и признак наличия сборок. После сохранения
  настройки перечитываются; запись JSON производится через временный файл и замену.
- `build_output` ищет ближайшую родительскую папку с файлом `.mpr` и выбирает
  `<папка с mpr>/wplc-build/YYYYMMDD-HHMMSS-ffffff`. Без `.mpr` сборка отменяется.
- `compile_source` и `rebuild` вызывают `tools/compile_program.py`. Рекомпиляция
  восстанавливает параметры из `build.json`; успешная сборка добавляется в каталог
  через `register_build`, без повторного поиска всех станций.

### Запуск, остановка и удаление

- `launch` создаёт отдельную копию runtime в `build/live/menu`, предлагает период
  цикла и параметры Snap7 (в меню порт по умолчанию 102), проверяет доступность порта.
  Для запуска требуется карта S7. В Linux используется доступный терминал либо текущий.
- Режим 3 в `launch` запускает `gateway`: OPC UA, Modbus TCP master и опционально
  Snap7 с общей памятью PLC. JSON настроек протоколов остаётся локальным;
  его путь хранится в `.local-validation/station-menu.json`. При первом запуске
  создаётся конфиг только с OPC UA. Контракты и ограничения: `PROTOCOLS.md`.
- `running_stations` учитывает только управляемые исполняемые файлы из `build/live`.
  Остановка проверяет путь и идентичность процесса: Windows handle/время создания,
  Linux `/proc`/pidfd. Состояние памяти остановленного контроллера теряется.
- `delete_menu` предлагает только допустимые отдельные каталоги сборок из сохранённого
  списка. `batch_selection` разбирает номера, диапазоны и выбор всех.
- `build_files` допускает `program.pkg` в папке с временной меткой внутри `wplc-build`
  рядом с `.mpr`, а также прежние такие папки в `build/compiled` и `build/recompiled`.
  Символические ссылки, junction/reparse points, вложенные папки и посторонние файлы
  запрещены. Разрешены только известные файлы результатов сборки.
- `delete_builds` сначала проверяет всю выборку, затем повторно проверяет каждую папку
  и запущенные управляемые процессы перед удалением. Удаляются отдельные проверенные
  файлы и затем пустая папка; рекурсивное удаление не используется. Проекты и `.mpr`
  сохраняются. Сборки в старых фиксированных каталогах не предлагаются к удалению.
- После удаления обновляются оба локальных каталога и связи исходных проектов.
  Пакетное удаление не транзакционно: завершённые удаления не откатываются при ошибке
  следующей папки. Нельзя одновременно запускать удаляемую сборку другим способом;
  обнаружение процессов ограничено управляемыми экземплярами.

Проверка: `python -m unittest discover -s tests -p 'test_*.py'`.
На момент записи памяти прошли 26 Python-тестов; тесты удаления используют временные папки.
Рабочие сборки пользователя при проверках удаления не удалялись.

По указанию пользователя после каждого завершённого этапа:

1. Выполнить проверки, соответствующие изменениям, и обновить описание результата и ограничений.
2. Проверить staged-содержимое через `python tools/check_publish.py --index`, создать коммит, затем проверить всю отправляемую историю через `python tools/check_publish.py --revision HEAD --history` и отправить её в `https://github.com/jet2/plc-wasm` (remote `origin`).
3. Сообщить пользователю результат и ссылку на коммит. При ошибке push явно сообщить об этом.

Не включать в коммиты локальный инструментарий Rust, каталог `target`, кэши и временные сборки из `build`.

## Запрет публикации SCL

Прямое требование пользователя: код SCL и его копии из рабочих исходных папок
не публиковать ни в каком виде; проверять с максимальной строгостью.

- Запрет касается целых файлов, фрагментов в тестах/документации/логах,
  переименованных и перекодированных копий, архивов, отчётов и скомпилированных
  программ станций. По консервативной политике синтетические SCL-примеры тоже локальные.
- SCL, предметные тесты, примеры, отчёты и сценарии находятся только в игнорируемом
  `.local-validation/` или `build/`. Не прикладывать их к PR, issues или сообщениям GitHub.
- Список исходных папок для сверки хранится в локальном `.publish-sources.json`.
  Если он отсутствует, пути недоступны или проверка не пройдена, push запрещён.
- Проверять Git-объекты, а не только расширения и рабочие файлы. Новые публикуемые
  пути требуют явного добавления в allowlist после проверки их содержимого.
- Установить `git config core.hooksPath .githooks`. Не обходить hook через
  `--no-verify`, переменные окружения или упрощённую CI-проверку.
- Проверка с `--structural-only` предназначена только для CI без доступа к
  оригиналам и не заменяет обязательную локальную сверку перед push.
